# BHU-DRISHTI Landing Page Implementation Plan

## 1. Outcome

Build a cinematic, credible landing page that begins with a scroll-controlled 3D map of India, narrows from India to Maharashtra to Nashik to one priority watershed structure, then transitions into a clean explanation of BHU-DRISHTI's evidence-fusion and prioritisation workflow.

The landing page must communicate one idea clearly:

> India already has watershed evidence at enormous scale. BHU-DRISHTI turns that evidence into explainable priorities and actions.

This plan covers the landing page only. It does not include real model inference, government-system integration, production authentication, live GIS services, or a working command centre.

## 2. Decisions already made

- Treat BHU-DRISHTI as a Pan-India product. Maharashtra and Nashik are one
  illustrative narrative path, not a limit on data coverage, schemas, APIs, or
  future command-centre filters.
- Keep the current React 19, TypeScript, Vite, and Tailwind CSS foundation.
- Use Maharashtra as the selected state and Nashik as the selected district for the narrative.
- Build the India object from geospatial boundary data; do not search for or ship a decorative India GLB that cannot separate accurately into states.
- Use separate extruded meshes for states so Maharashtra can physically lift out of India.
- Use the Maharashtra district topology for the second drill-down layer.
- Use a single pinned 3D sequence for approximately 4-5 viewport heights of scroll input, followed by normal document scrolling.
- Keep the 3D map as the dominant opening visual. Do not add feature cards to the hero.
- Use muted aqua and green as the brand palette, with restrained amber, terracotta, and blue-grey only for operational statuses.
- Keep all numerical site, district, and AI examples in a clearly identified illustrative demo dataset until official data is available.
- Treat accessibility, reduced motion, mobile fallbacks, and non-WebGL fallbacks as part of the implementation rather than later polish.

## 3. Boundary-data decision

### Assessment of `udit-001/india-maps-data`

The repository is a good technical fit for a visual prototype because it provides:

- TopoJSON and GeoJSON formats.
- An all-India topology containing district geometries with `district`, `dt_code`, `st_nm`, `st_code`, and `year` properties.
- Individual state files with district boundaries.
- A Maharashtra file that includes Nashik.
- Shared TopoJSON arcs, which are useful for merging districts into state outlines without duplicated internal borders.

It is not a downloadable 3D model. The 3D form must be generated by projecting its geographic coordinates into a local plane and extruding each state polygon in Three.js.

The repository is suitable only conditionally:

- The README says the data was curated from unspecified public sources and was not created by the repository owner.
- The README frames usage as personal and does not present an explicit data licence.
- Feature metadata contains mixed vintages such as `2011_c`, `2019`, and `update2014`, so administrative names and boundaries cannot be assumed current.
- The all-India TopoJSON is roughly 866 KiB uncompressed and Maharashtra roughly 95 KiB, so the raw files should not be fetched and processed on every page load.
- A government-facing map needs a political-boundary compliance review. Survey of India guidance states that Survey of India published maps or digital boundary data are the standard for political maps of India.

### Final source policy

Use the linked repository to unblock the geometry prototype, but place a hard approval gate before public or judged deployment:

1. Verify that reuse and redistribution are permitted.
2. Compare the national outline and state/UT boundaries against current Survey of India material.
3. Replace the prototype source with Survey of India administrative boundary data if provenance, licensing, names, or geometry cannot be verified.
4. Preserve source URL, full commit SHA, acquisition date, processing steps, and any attribution in a checked-in provenance note.

### Asset acquisition and preparation

When implementation begins:

1. Clone the source repository into a temporary/vendor-review directory, not directly under `src`.
2. Resolve and record the full commit SHA rather than depending on a moving `main` branch or an unpinned CDN URL.
3. Retain only the all-India TopoJSON and Maharashtra district TopoJSON needed for this experience.
4. Inspect geometry validity, state/UT count, required property names, MultiPolygon handling, holes, islands, and Nashik presence.
5. Group the all-India district geometries by `st_nm` and merge each group into one state/UT MultiPolygon.
6. Normalise names and assign stable internal IDs without erasing the original source attributes.
7. Project longitude/latitude into a consistent planar coordinate space, recenter the whole country around the scene origin, and preserve the transform metadata needed to place markers.
8. Simplify geometry conservatively and visually compare it with the source at desktop and mobile sizes. Small islands and narrow coastal geometry must not disappear silently.
9. Export two small, app-owned render assets:
   - National state/UT polygons, already merged and projected.
   - Maharashtra district polygons, already projected in the same coordinate system.
10. Generate a static SVG/poster from the same processed geometry for reduced-motion and non-WebGL fallback modes.
11. Record file sizes and fail the preprocessing check if expected states, Maharashtra, or Nashik are missing.

Preprocessing should happen in a repeatable script during asset updates, not in the browser on every visit.

## 4. Technical approach

### Runtime libraries

- `three`: scene, materials, lights, cameras, shapes, and extrusion.
- `@react-three/fiber` version 9: React renderer compatible with the existing React 19 foundation.
- `gsap`, `@gsap/react`, and ScrollTrigger: one master, scrubbed and pinned narrative timeline with React-safe cleanup.

### Asset-build libraries

- `topojson-client`: convert topology to features, merge district polygons by state, and create boundary meshes.
- `d3-geo`: consistent projection and fitting before export.
- A TopoJSON simplification tool only if visual inspection proves the source geometry too heavy.

Keep TopoJSON and projection tooling out of the runtime bundle by using it only in the preprocessing script.

### Rendering model

- One orthographic camera for the editorial/isometric look. A perspective camera may be tested in the spike, but the orthographic option is the default because it keeps state shapes legible during zooms.
- One mesh/group per state or union territory.
- Shallow extrusion for the national map, with distinct top and side materials.
- Very small physical spacing/outline separation between state pieces; do not scale pieces apart and distort India.
- Maharashtra animates upward on the Z axis, then left in the viewport. Other states move slightly backward and fade.
- Maharashtra districts appear as shallow overlays or separate thin meshes only after the state separation begins.
- Nashik receives a brighter top material and stronger outline; other districts reduce opacity.
- Structure markers use instanced geometry or lightweight sprites, not individual complex React components.
- Camera, mesh positions, opacity, and marker emphasis are driven from one normalised story progress value.
- Decorative ambient particles, terrain textures, bloom, and real-time shadows are out of scope for the first pass.

### Animation architecture

Use one scroll owner and one timeline. The pinned wrapper remains structurally stable; only its children animate. This avoids competing scroll listeners and common pinning measurement problems.

The timeline should expose named chapters rather than scattering magic progress values through components:

1. `india-intro`
2. `evidence-scale`
3. `triage-question`
4. `maharashtra-focus`
5. `nashik-focus`
6. `priority-site`
7. `solution-handoff`

React should not rerender on every scroll tick. Scene objects animate through refs, and accessible DOM copy changes only at chapter boundaries or through efficiently updated CSS variables.

## 5. Information architecture and narrative

### Persistent header

- Top-left: BHU-DRISHTI identity mark and wordmark.
- Top-right desktop navigation: About, How It Works, Impact, Login.
- About anchors to the monitoring-gap section.
- How It Works anchors to the evidence-fusion workflow.
- Impact anchors to the output-to-outcome section.
- Login points to a real `/login` or configured authentication handoff. If that route is not ready, show an honest demo-access state; never ship a dead link.
- Header becomes slightly more opaque once the page leaves the opening frame but stays visually quiet.

### Act I: pinned India story

The pinned experience occupies one fixed visual stage while the user supplies approximately 4-5 viewport heights of scroll.

#### Chapter 1 — India as the hero

- Nearly empty viewport with the 3D India model centered.
- Headline: “From watershed data to watershed decisions.”
- Subtext: “AI-powered interpretation and prioritisation for India's watershed monitoring ecosystem.”
- Small “Scroll to explore” prompt.
- No feature cards, floating dashboard windows, or large navigation panel.

#### Chapter 2 — establish scale

- Camera moves closer without aggressive rotation.
- A restrained sequence introduces the verified national figures: 1,220 watershed projects and approximately 1.24 lakh water-harvesting structures.
- A third qualitative statement can mention geo-tagged observations, but no unsupported quantity should be invented.
- Sparse markers appear across the map.
- A visible source/verification note must accompany official programme figures before launch.

#### Chapter 3 — introduce triage

- Markers resolve into Healthy, Monitor, High priority, and Uncertain examples.
- Each status uses a label/icon treatment as well as colour.
- Copy: “Every structure is evidence. Not every structure requires attention.”
- Follow with: “So where should officials look first?”

#### Chapter 4 — India to Maharashtra

- Maharashtra highlights while the rest of India dims.
- Breadcrumb transitions from India to Maharashtra.
- Maharashtra lifts above the other pieces, the national group moves backward, and the selected state settles to the left.
- A right-side information panel introduces illustrative state-level project, structure, and attention counts.
- Every non-official number carries an “Illustrative demo” label.

#### Chapter 5 — Maharashtra to Nashik

- District outlines fade in only after the state is isolated.
- Nashik highlights; other districts remain visible but subdued.
- The panel switches to illustrative Nashik monitoring and priority figures.
- Watershed boundaries are represented only if a real or intentionally fabricated demo boundary asset exists. District polygons must not be mislabeled as watershed boundaries.

#### Chapter 6 — priority structure

- A small set of structure markers appears inside Nashik.
- One high-priority marker pulses gently; pulse stops for reduced-motion users.
- The panel presents possible siltation, reduced water presence, weak vegetation recovery, confidence, and recommended field inspection.
- Use cautious language: “possible issue” and “inspection recommended,” not a definitive structural diagnosis.
- End on: “But how does BHU-DRISHTI know?”

#### Chapter 7 — release the page

- The pinned scene completes before normal scrolling begins.
- Maharashtra remains briefly visible as the solution section enters, then fades naturally.
- The handoff must not cause a vertical jump or trap the user in the pin.

### Act II: educational explanation

Each section introduces one new concept and avoids dense card grids.

1. **Evidence is not understanding**
   - Show what Drishti and Bhuvan/Srishti already provide: geo-tagged field evidence and geospatial context.
   - Surface the questions that still require interpretation.

2. **The BHU-DRISHTI intelligence layer**
   - Present BHU-DRISHTI between existing evidence sources and decisions.
   - Explain that it augments rather than replaces current government systems.

3. **Four evidence inputs**
   - Field image: visible water, vegetation, siltation, and erosion.
   - Satellite: NDVI, NDWI, and temporal change.
   - Rainfall: deviation from expected conditions.
   - GIS: slope, drainage, soil, and terrain.
   - These may use four tiles because the comparison is meaningful; keep each concise.

4. **Evidence fusion**
   - Animate the four inputs toward a single reasoning panel.
   - Conclude: “Multiple independent signals indicate deterioration.”
   - Make clear this is not merely an image classifier.

5. **Explainable priority, not a mystery score**
   - Fade or cross out a bare `42/100` score.
   - Replace it with priority, contributing evidence, confidence, and recommended action.

6. **Human in the loop**
   - Show high confidence, review recommended, and human inspection required states.
   - State explicitly that BHU-DRISHTI supports engineers and officials; it does not replace them.

7. **Prioritisation at scale**
   - Reduce the visual from 124,000+ structures to a reviewable priority queue.
   - Do not imply that the illustrative funnel is an official current result.

8. **Impact and rainfall normalisation**
   - Compare before/after NDVI, NDWI, water presence, and vegetation.
   - Explain that greener satellite imagery may reflect rainfall or seasonality rather than intervention impact.

9. **Complete workflow**
   - Drishti photo → computer vision → GIS/satellite/rainfall → evidence fusion → condition → priority → action.

### Act III: product credibility

1. **Plan, Monitor, Evaluate, Act**
   - Four concise product modes with one-line outcomes.

2. **Product preview**
   - Geographic overview, ranked priority queue, and site evidence/explanation view.
   - Use labelled mock data and a coherent single scenario across all previews.

3. **Existing-system integration**
   - Diagram Drishti and Bhuvan/Srishti feeding BHU-DRISHTI.
   - Avoid claiming completed integrations.

4. **Users at different levels**
   - National officials: compare programmes and regions.
   - District officials: know what requires attention today.
   - Field staff: understand how observations support action.

5. **Output to outcome**
   - “Don't only measure how many structures were built. Measure whether watersheds improved.”
   - Focus on water retention, vegetation, land condition, structure performance, and long-term impact.

### Act IV: cinematic close

- Return to the India model, now populated with restrained intelligence markers.
- Restate the pitch: “Drishti captures the ground. Bhuvan shows where it is. BHU-DRISHTI explains what it means and what should happen next.”
- Primary CTA: Enter Command Centre.
- Secondary CTA: Explore Demo.
- Optional tertiary link: View Architecture.
- Footer: BHU-DRISHTI, Smart India Hackathon 2026, SIH26015, Team Lethals, and essential project links.
- CTA destinations must exist or be marked clearly as demo previews.

## 6. Visual system

### Direction

Use a muted “watershed intelligence” palette: pale mineral backgrounds, aqua for water/data, forest green for institutional confidence, and soft sage for depth. The page should feel calm, technical, and credible rather than neon, glossy, or militaristic.

### Proposed core tokens

| Role           | Colour    | Use                                   |
| -------------- | --------- | ------------------------------------- |
| Canvas         | `#F2F6F3` | Primary page background               |
| Raised surface | `#E5EEE9` | Panels and section separation         |
| Deep ink       | `#17332D` | Body and headings                     |
| Deep aqua      | `#285F60` | Links, focus, data emphasis           |
| Forest         | `#305D49` | Brand and primary actions             |
| Muted aqua     | `#5E9895` | Map top faces and decorative data     |
| Sage           | `#88A992` | Secondary map faces and quiet accents |
| Pale water     | `#BFD8D2` | Lines, dividers, and inactive data    |

### Status tokens

| Status        | Colour    | Required secondary cue                    |
| ------------- | --------- | ----------------------------------------- |
| Healthy       | `#39725B` | Check/leaf mark and “Healthy” label       |
| Monitor       | `#8A6228` | Clock/eye mark and “Monitor” label        |
| High priority | `#A64F45` | Alert mark and “High priority” label      |
| Uncertain     | `#4E6F79` | Question mark and “Review required” label |

Muted aqua and sage are decorative colours and must not carry small text on the light canvas. Deep ink, deep aqua, forest, and the darker status colours are the text/focus options. Validate every final foreground/background pairing against WCAG AA.

### Type and composition

- Retain the current Avenir Next/system display stack and Inter/system sans stack for the first pass; do not add a font download until the visual prototype proves it necessary.
- Use large editorial headlines, compact uppercase labels, and tabular numerals for statistics.
- Use generous whitespace and thin low-contrast dividers.
- Avoid glassmorphism, heavy gradients, luminous neon glows, large rounded card grids, and dashboard chrome in the hero.
- Keep motion slow and intentional: lift, focus, fade, camera dolly, and one restrained marker pulse.

- The static fallback is generated from the same map data as the 3D scene.
- Live product APIs can later replace `demoScenario.ts` without rewriting the page layout.

## 8. Responsive and fallback behaviour

### Desktop and large tablet

- Full pinned 3D sequence.
- Maharashtra moves left and the information panel opens on the right.
- Navigation remains in the top-right.

### Small tablet and mobile

- Preserve the India → Maharashtra → Nashik → site story, but shorten the scroll distance.
- Keep the map above and use a bottom information sheet instead of a narrow side panel.
- Reduce marker count and device pixel ratio.
- Collapse navigation into a compact accessible menu after verifying it does not cover the pinned copy.
- Use dynamic viewport units so mobile browser chrome does not create jumps.

### Reduced motion

- Do not pin for several viewport heights.
- Use the generated poster/SVG or a static 3D frame.
- Present the same chapters as a normal sequence of semantic sections with simple opacity changes or no animation.
- Disable pulsing, long camera travel, and scrubbed movement.

### WebGL unavailable or weak device

- Detect renderer creation failure and switch immediately to the static poster.
- Do not show a blank canvas or error message as the hero.
- Preserve all copy, links, statuses, and narrative in normal HTML.

## 9. Accessibility requirements

- Provide a “Skip interactive map story” link before the pinned experience.
- The canvas is visual support, not the only source of information; expose equivalent semantic copy in the DOM.
- Do not trap keyboard focus during the pinned sequence.
- Pause or reduce canvas work when the document is hidden or the scene is no longer visible.
- Respect `prefers-reduced-motion` from the first render, not after animation starts.
- Pair every operational colour with text and an icon/shape.
- Maintain visible keyboard focus and WCAG AA contrast.
- Use real headings in a logical order and landmark elements for header, main content, navigation, and footer.
- Announce chapter changes only if user testing shows it is helpful; avoid a noisy live region during scroll.
- Make CTAs descriptive and ensure anchor navigation restores focus predictably.

## 10. Performance budget

- Render the header and hero copy immediately; load the 3D implementation as a separate chunk with the poster underneath it.
- Preprocess geometry so the browser does not merge the full district dataset at runtime.
- Target a national map render asset below 200 KiB compressed and Maharashtra below 50 KiB compressed, subject to boundary fidelity.
- Cap canvas device pixel ratio around 1.5 on desktop and lower it on mobile/slow devices.
- Avoid real-time shadows, large textures, post-processing, and per-marker draw calls.
- Reuse materials and geometry and use instancing for markers.
- Dispose of geometries, materials, timelines, listeners, and ScrollTriggers on unmount.
- Keep cumulative layout shift below 0.1 by reserving the pinned stage size and fallback dimensions.
- Target LCP below 2.5 seconds on a representative mid-range mobile profile and a smooth desktop sequence without repeated long tasks.
- Run the scene only while needed; the normal content sections should not pay continuous animation cost.

## 11. Demo-data and content governance

Create a single typed demo scenario and classify every value as one of:

- `official`: backed by a recorded source and retrieval date.
- `derived`: calculated from an official source, with the method recorded.
- `illustrative`: invented only to explain the product interaction.

Rules:

- Verify the 1,220-project and approximately 1.24-lakh-structure figures against a primary government source before public launch.
- Label Maharashtra, Nashik, site, priority-queue, confidence, NDVI, NDWI, and rainfall values as illustrative unless real approved data is supplied.
- Keep one consistent sample site across the 3D story, evidence-fusion panel, explanation, priority queue, and product preview.
- Avoid definitive engineering or causal claims. The language should describe visible indicators, confidence, correlation, and recommended verification.
- Include a compact “Demo data” disclosure without weakening the core narrative.
- Review all uses of Drishti, Srishti, Bhuvan, WDC-PMKSY, NRSC, and ISRO names for accuracy and attribution.

## 12. Implementation phases and exit criteria

### Phase 0 — source and story lock

Deliverables:

- Boundary-source decision and provenance record.
- Verified national outline/state count and Maharashtra/Nashik presence.
- Approved chapter list, final hero copy, section headings, CTA destinations, and demo-data labels.
- Decision on whether `/login`, Command Centre, and Explore Demo destinations are real routes or explicit previews.

Exit criteria:

- No unlicensed or unverified map asset is approved for release.
- No dead navigation item or CTA remains in the specification.
- Every displayed number has a classification and source state.

### Phase 1 — geometry spike

Deliverables:

- Repeatable preprocessing pipeline.
- Separate extruded state pieces from the processed national data.
- Maharashtra lift/fade prototype.
- Maharashtra districts and Nashik highlight.
- Static SVG/poster fallback.

Exit criteria:

- All expected states/UTs render in correct relative positions, including islands.
- No visible polygon holes, inverted faces, broken MultiPolygons, or district seams at target sizes.
- Maharashtra can separate without distorting neighbouring states.
- The fallback matches the 3D silhouette.

### Phase 2 — visual foundation and static page

Deliverables:

- Final design tokens and type scale.
- Semantic header, all normal-scroll sections, footer, and responsive layout with no animation.
- Typed landing copy and demo scenario.

Exit criteria:

- The entire story is understandable with JavaScript animation disabled.
- Colour contrast, heading order, navigation, and responsive composition pass review.

### Phase 3 — pinned narrative

Deliverables:

- One master ScrollTrigger timeline with named chapters.
- Camera movement, marker reveal, status transition, Maharashtra separation, Nashik focus, site focus, and handoff.
- DOM panel transitions synchronised with the scene.

Exit criteria:

- Forward and reverse scrolling are deterministic.
- Fast scroll, refresh mid-page, resize, orientation change, and browser back navigation do not leave the scene in the wrong state.
- Entering and leaving the pinned section produces no jump.

### Phase 4 — educational and product motion

Deliverables:

- Evidence-input flow, evidence-fusion convergence, explainability comparison, priority funnel, before/after comparison, and closing India callback.
- Motion limited to the one idea each section needs to explain.

Exit criteria:

- The normal page remains readable and responsive without becoming another continuous scroll experiment.
- Animations clarify relationships and do not delay access to content.

### Phase 5 — accessibility and device adaptation

Deliverables:

- Reduced-motion version.
- Mobile narrative and bottom-sheet layout.
- WebGL failure/low-power fallback.
- Keyboard, screen-reader, zoom, and contrast fixes.

Exit criteria:

- All narrative content and actions are available without the canvas.
- The page works at 200% zoom, with keyboard only, and with reduced motion enabled.
- Mobile browser chrome and orientation changes do not break the pinned stage.

### Phase 6 — performance and verification

Deliverables:

- Geometry/file-size report.
- Bundle analysis and route/chunk review.
- Lighthouse/Web Vitals profile on representative desktop and mid-range mobile settings.
- Automated and manual test suite results.
- Boundary and content sign-off.

Exit criteria:

- Performance budgets are met or documented trade-offs are approved.
- There are no console errors, leaked animation handles, blank-canvas states, or broken links.
- Final boundary geometry and programme figures have traceable sources.

## 13. Test plan

### Unit tests

- Topology grouping produces the expected unique state/UT IDs.
- Polygon, MultiPolygon, holes, and islands convert correctly.
- Projection gives stable bounds and marker coordinates.
- Maharashtra and Nashik lookup succeeds.
- Story progress resolves to the correct chapter at all boundaries.
- Demo-data classifications are present for every displayed metric.

### Component tests

- Header anchors and menu behaviour.
- Correct content for each story chapter.
- Statuses include non-colour cues.
- Reduced-motion and fallback branches render equivalent content.
- CTA and login behaviour match the configured destinations.

### Browser and visual tests

- Desktop Chromium, Firefox, and Safari.
- Current mobile Safari and Chrome; portrait and landscape.
- Forward/reverse scroll, trackpad, mouse wheel, touch, Page Up/Down, and scrollbar dragging.
- Reload at the middle/end of the pinned section.
- Resize while pinned and rotate a mobile device.
- WebGL disabled and renderer creation failure.
- `prefers-reduced-motion`, high contrast where available, and 200% zoom.
- Screenshot checkpoints for each named chapter and key responsive breakpoint.

### Manual content checks

- India political-boundary review.
- Names and labels review.
- Official/illustrative data disclosure review.
- Claim-safety review for structural condition, impact, and AI confidence.
- No suggestion that integrations or AI models are already deployed when they are not.

## 14. Key risks and mitigations

| Risk                                         | Mitigation                                                                                                                |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Prototype map has unclear licence/provenance | Use only behind the Phase 0 gate; prefer Survey of India data for release                                                 |
| Boundary or district data is stale           | Validate against current official material; record vintage; avoid presenting prototype geometry as authoritative          |
| Raw topology makes the hero slow             | Pre-merge, project, simplify, and export a render-specific asset                                                          |
| 3D scroll sequence feels gimmicky            | Keep one camera language, no free orbit, restrained motion, and a short pinned act                                        |
| Scroll pin breaks on mobile/Safari           | Use one pin owner, stable wrapper dimensions, viewport-unit testing, refresh on layout changes, and a shorter mobile mode |
| Canvas excludes assistive technology         | Mirror the narrative in semantic DOM and provide skip/static paths                                                        |
| Colour statuses are ambiguous                | Add labels and symbols and validate contrast                                                                              |
| Demo metrics are mistaken for live results   | Centralise and label illustrative data; add a visible disclosure                                                          |
| AI claims sound unsafe                       | Use explainable indicators, confidence, and human-review language                                                         |
| Three.js bundle dominates first load         | Split the scene, show a poster immediately, preprocess assets, and avoid optional visual libraries                        |

## 15. Definition of done

The landing page is complete when:

- The opening viewport is dominated by a correctly shaped, separate-piece 3D India model with the required minimal header and hero copy.
- Scroll smoothly tells the India → Maharashtra → Nashik → priority-site story and then releases into normal page flow.
- The rest of the page clearly explains the monitoring gap, evidence fusion, explainable priority, human review, impact analysis, application workflow, and existing-system role.
- The visual system consistently uses the approved muted aqua/green palette.
- All official and illustrative data is distinguishable and traceable.
- The experience remains understandable and usable on mobile, with reduced motion, with keyboard/screen reader access, and without WebGL.
- Boundaries are approved for the intended government/SIH context.
- Performance, browser, accessibility, visual, and content checks pass.
- Navigation and CTAs lead somewhere real and contain no placeholder promises presented as finished functionality.
